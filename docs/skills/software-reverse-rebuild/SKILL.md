# 软件逆向研究与重建

目标是**弄清楚一个产品做了什么、怎么交互、接口长什么样，然后自己设计实现**，不是复制别人的代码。

## 0. 先确认边界（每次开始都要做）

动手前用一两句话和员工确认：

- 研究对象是什么、我们有没有权限研究它（自己公司的系统、员工自己的试用账号、公开页面）。
- 不做的事：绕过登录、破解授权或加密、批量抓取别人的数据、复制对方的专有代码 / 图片 / 文案 / 商标。
  重建时界面、命名、图标都用我们自己的设计。
- 凭证：浏览器里的 Cookie、令牌、密码不写进文档、代码和回答（系统会自动打码，看到 `***` 就是被打码了，不要想办法还原）。

有不确定的地方停下来问员工，不要自己猜。

## 1. 摸清能用的工具

`load_skill` 返回的「这个技能要用的连接器」一节列出了**真实连上的连接器和它们的真实工具名**，只用那里列出的名字：

| 连接器（示例 ID） | 用途 | 没连上时 |
| --- | --- | --- |
| playwright | 打开网页、点按、截图、看网络请求 | 让员工提供截图、HAR 文件或接口文档 |
| rea | 分析桌面客户端程序（模块、函数、字符串、协议） | 跳过客户端分析，只做网页部分 |
| craft | 生成项目骨架、组件 | 用 write_file / multi_edit 自己写 |

用 `update_plan` 把下面几个阶段列成计划，每完成一段更新一次（程序中途被关后能从断点接着做）。

## 2. 侦察：功能和页面清单

- 从首页开始，按导航把主要页面走一遍，每个页面记：路径、用途、主要组件、能做的操作、空状态和报错长什么样。
- 互不相关的模块（文件列表、分享、权限、搜索、设置……）可以用 `spawn_agent` 开几个**只读**子代理同时调研，
  每个子代理的 prompt 写清：看哪个模块、要交回什么（页面清单 / 操作列表 / 截图路径）。
- 产出：`re/inventory.md`（功能清单，按模块分组，每条标「已确认 / 推测」）。

## 3. 接口和数据模型

- 在页面上做一次典型操作（上传、新建文件夹、分享、改权限），记录对应的网络请求：方法、路径、查询参数、请求体和返回体的**结构**
  （字段名、类型、是否必填），不要记录真实的令牌、Cookie、个人数据。
- 归纳实体和关系：用户、组织、文件、文件夹、版本、分享链接、权限、评论、活动记录……
- 产出：`re/api.yaml`（OpenAPI 3 草稿，只写我们观察到的，推测的加 `x-inferred: true`），`re/data-model.md`。

## 4. 客户端分析（有授权且 rea 连上时）

- 只看结构和协议：模块划分、同步机制、本地缓存格式、和服务器通信的方式。
- 不提取、不复制对方的代码和资源。
- 产出：`re/client-notes.md`。

## 5. 重建方案

- 对照功能清单按优先级分三档（必须有 / 应该有 / 以后再说），写清每档的验收标准。
- 架构：前端、后端、存储、鉴权、文件存储、搜索、通知；说明为什么这么选。
- 里程碑：每个里程碑能单独演示。
- 产出：`re/rebuild-plan.md`，交员工确认后再动手写代码。

## 6. 实现与验证

- 按里程碑实现。改代码用 `edit_file` / `multi_edit`，用 `grep` 找调用点，用 `git_status` / `git_diff` 看改动，`git_commit` 提交（提交前给员工看 diff）。
- 每完成一个功能跑项目的测试；网页功能可以用 playwright 走一遍和清单对照。
- 如实报告：没跑的测试不说通过，没做完的功能不说完成。

## 交付物

`re/` 目录下：`inventory.md`、`api.yaml`、`data-model.md`、`client-notes.md`（可选）、`rebuild-plan.md`，以及代码仓库本身。
回答员工时先给一段总结，再列文件路径。
