# 方案：运维代理自升级 + 补 PATH（backlog A）

> 2026-11-12 草案，待确认后开发。对应 `docs/backlog.md` 的 A。

## 1. 要解决的问题

| 问题 | 现状 | 后果 |
| --- | --- | --- |
| 老电脑敲不了 `flyknit` | 把员工端目录加进系统 PATH 只有安装程序做；代理升级员工端时不做 | 命令行功能之前装的电脑，升级后仍提示「不是内部或外部命令」 |
| 运维代理自己不升级 | `ClientUpdater` 只整目录替换员工端，`C:\Program Files\FlyknitAgent\FlyknitAgent.exe` 从不更新 | 代理里的新功能（补 PATH、顺带装 WebView2 运行时……）到不了已装好的电脑 |

已经在跑的旧代理没有自升级代码，所以必须分成两步：

1. **一次性「搭桥」**：把旧代理换成新代理（第 3 节）；
2. **以后自动**：新代理随员工端一起自升级（第 4 节）。

## 2. 关键事实（看代码确认过的）

- 员工端发布包里**已经带着新代理**：`FlyknitBuddy\agent\FlyknitAgent.exe`（`publish-client.ps1` 生成，安装程序从这里装代理）。
  代理升级员工端时下载的就是这个包，并校验过 SHA-256。所以**不需要新的下载通道**。
- 代理暂存目录 `C:\Program Files\FlyknitAgent\client-updates` 只有 SYSTEM 和管理员能写，员工动不了（`ClientUpdater` 注释里写了为什么不用 ProgramData）。
- 后台已经知道每台代理的版本（`/agent/poll` 上报 `agent_version`）。
- **不能直接用「安装软件」任务推安装程序**：
  `Setup.exe` 第一步就 `sc stop FlyknitAgent`。代理收到停止信号后，`ProcessRunner` 会把它启动的子进程连同子孙一起结束（`Kill(entireProcessTree: true)`），
  于是安装程序刚停掉代理就被杀，电脑停在「代理已停止、员工端没换」的状态，要等重启才恢复。backlog 里原来写的这条路要改。

## 3. 第一步：给旧代理「搭桥」（一次性）

**做法**：安装程序加一个参数 `/deferred`（只能和 `/S` 一起用）：

1. 被代理以「安装软件」任务启动后，把自己复制到 `C:\Program Files\FlyknitAgent\setup-deferred\`（只有管理员能写，
   不放 `C:\Windows\Temp`：那里普通用户能放文件，单文件程序解压原生库时有被抢先放 DLL 的风险）；
2. 以分离的方式启动这份副本（`/S /deferred-run <父进程 ID>`），然后**立即退出、返回 0**。任务回报「已安排安装」；
3. 副本等代理把任务回报完、父进程退出，再多等 10 秒，然后照常 `/S` 静默安装：停代理 → 换员工端 → 装新代理 → 启动代理；
4. 结果写进 `C:\ProgramData\Flyknit\setup.log`。成功没成功，看后台这台代理的版本有没有变。

副本的父进程（`Setup.exe`）已经退出，代理停止时不会再被连带结束。

**后台怎么推**（两种，先做 a）：

- a. **手动**：IT 在「员工端版本」页下载安装程序 `.exe`，上传到「软件库」，静默参数填 `/S /deferred`，勾选代理版本旧的电脑下发「安装软件」。
  帮助中心写一页步骤。
- b. **一键**：设备 / 代理列表加按钮「升级旧代理」：服务端用当前版本生成安装程序、登记成软件包、对选中电脑下发同样的任务。
  省掉手动上传，但要多写一块服务端（生成包、缓存、清理），放到 a 验证过之后。

**没有代理的电脑**（免安装版、代理没装上）用不了这条路，只能现场装一次（E 已经能在后台把它们筛出来）。

## 4. 第二步：新代理随员工端自升级

### 4.1 什么时候升

在 `ClientUpdater` 把员工端新版本**解开、校验通过之后**：

1. 读暂存目录里 `agent\FlyknitAgent.exe` 的版本，**只有严格比自己新才升**（不降级，版本相同不动）；
2. 把它复制到 `C:\Program Files\FlyknitAgent\update\FlyknitAgent.exe`（只有 SYSTEM 和管理员能写）；
3. 等「空闲」再换：没有正在执行的任务、员工端替换已经完成或不在进行。

### 4.2 怎么换（正在跑的 exe 不能直接覆盖）

1. 代理把**自己**（当前版本，已知能跑）复制成 `update\FlyknitAgentUpdate.exe`，以分离方式启动：`--complete-update <自己的进程 ID>`；
2. 代理正常停止服务（报告 SERVICE_STOPPED，不算崩溃）；
3. 更新助手等原进程退出，然后：
   - `FlyknitAgent.exe` → 改名为 `FlyknitAgent.exe.old`（Windows 允许改名正在用的文件，这时它也已经退出了）；
   - `update\FlyknitAgent.exe` → 移动成 `FlyknitAgent.exe`；
   - `sc start FlyknitAgent`；
4. **健康检查**：新代理启动后第一次成功和服务端通信（注册或领任务），就写 `update\healthy` 标记。
   更新助手最多等 3 分钟：
   - 等到了：删掉 `.old`，记日志，退出；
   - 没等到（启动失败、崩溃、连不上）：停服务 → 把 `.old` 改回 `FlyknitAgent.exe` → 启动 → 写日志，并把这个版本记进 `update\skip`，**以后不再尝试同一个版本**。

为什么更新助手用旧版本而不是新版本：新版本要是坏的，用它来回滚也会失败。

### 4.3 补 PATH

- 员工端替换成功后，以及代理每次启动时，检查员工端目录里有没有 `flyknit.exe`。
  有就用安装程序的 `PathList`（链接同一份源文件）把这个目录加进系统 PATH，然后广播 `WM_SETTINGCHANGE`。
- 只加这一个目录，去重、大小写不敏感；已经在 PATH 里就什么都不做。目录来自代理自己的配置（安装程序写的 `client_dir`），不接受服务端或员工给的路径。
- 这一项不受下面的开关控制：只改 PATH、可逆、风险低。

### 4.4 总开关（服务端执行，默认关）

- 后台「安全中心」加一项「**运维代理自动升级**」，默认关，可以按部门 / 单台电脑设置（沿用三层设置）。
- 服务端在 `/agent/poll` 的回应里带 `self_update: true/false`，代理只按这个值决定升不升。
  老服务端不带这个字段，按「关」处理。
- 关着的时候：代理只补 PATH，不换自己；后台照样能看到哪些代理版本旧。

### 4.5 后台

- 代理列表显示版本，加筛选「代理版本旧」：比当前发布的员工端包里的代理版本旧的。服务端在上传 / 发布版本时从 zip 里读出代理版本。
- 代理版本变了写一条审计（谁、从哪个版本到哪个版本、自升级还是搭桥）。
- 更新助手回滚过的，代理下次领任务时上报 `self_update_failed: <版本>`，设备详情里显示「升级到 x 失败，已回到 y」。

## 5. 安全

| 风险 | 处理 |
| --- | --- |
| 有人借代理的手把恶意程序装成 SYSTEM 服务 | 新代理只来自代理自己下载、SHA-256 校验过的员工端包，而且只在 SYSTEM 和管理员才能写的目录里中转。和现在「代理替员工端升级」的信任链相同，没有新增入口 |
| 服务端被攻破后推恶意代理 | 现在服务端本来就能下发「安装软件」任务、以 SYSTEM 身份运行任意安装包，自升级没有扩大能力。另外总开关默认关，版本变化写审计 |
| 降级攻击（推一个有漏洞的旧版） | 只升不降 |
| 换坏了代理再也连不回来 | 健康检查加自动回滚；坏版本记进 skip 不再重试；服务的失败重启策略照旧 |
| 搭桥副本被抢先放 DLL | 副本放在 Program Files 下只有管理员能写的目录，不放 Windows\Temp |
| 改 PATH 影响别的软件 | 只追加这一个目录，不动别的项；卸载时由安装程序去掉 |

## 6. 改哪里

| 层 | 文件 | 内容 |
| --- | --- | --- |
| 安装程序 | `Flyknit.Setup/Program.cs`、`Installer.cs` | `/deferred`、`/deferred-run`；副本目录；日志 |
| 代理 | `Flyknit.Agent/ClientUpdater.cs` | 解开后取出新代理、员工端替换成功后补 PATH |
| 代理 | 新增 `Flyknit.Agent/SelfUpdater.cs` | 判断版本、空闲时启动更新助手、停服务；`--complete-update` 模式（替换、启动、健康检查、回滚） |
| 代理 | `Program.cs`、`Worker.cs` | `--complete-update` 入口；首次通信成功写健康标记；启动时补 PATH；读 poll 里的 `self_update` |
| 代理 | `Flyknit.Agent.csproj` | 链接 `Flyknit.Setup/PathList.cs` |
| 服务端 | `routers/agents.py`、`services/device_security.py`、`releases.py` | poll 回应加 `self_update`；安全中心新项（默认关）；发布时读出包里的代理版本；版本变化写审计 |
| 后台 | 安全中心、设备 / 代理列表 | 开关；「代理版本旧」筛选；失败提示 |
| 文档 | 帮助中心「装到员工电脑」 | 搭桥步骤、开关说明、验收方法 |

## 7. 测试

- **单元测试**（Core 测试项目链接源文件，和现在测 `Payload`、`AgentSettings` 的方式一样）：
  - 版本比较：只升不降、相同不动、认不出的版本不升、skip 里的版本不升；
  - 安装程序参数：`/deferred` 必须和 `/S` 一起；`/deferred-run` 要带进程 ID；
  - PATH：已在 PATH 不重复加、没有 `flyknit.exe` 不加（`PathList` 已有测试，补这两条）；
  - 更新助手的状态判断（拆成纯函数）：健康标记到了 → 收尾；超时 → 回滚并记 skip。
- **服务端**：开关默认关、三层覆盖生效；poll 回应字段；发布时读包里代理版本；「代理版本旧」筛选；审计。
- **Windows 虚拟机实测**（这部分只能在真机上做，做完才算完成）：
  1. 装一个旧版（命令行功能之前的），用「安装软件」+ `/S /deferred` 推新安装程序 → 代理版本变新、`flyknit --version` 能跑；
  2. 打开开关，发布一个新版本 → 员工端和代理都升上去，`setup.log` / `agent.log` 记录完整；
  3. 故意发布一个启动就崩的代理 → 3 分钟内回滚到原版本，后台显示失败，下个周期不再重试同一个版本；
  4. 升级中途断网、断电重启 → 代理能起来（最坏是旧版本）；
  5. 开关关着 → 只补 PATH、不换代理。
