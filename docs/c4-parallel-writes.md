# 方案：VNext 第 4 期——并行写（隔离）（backlog C4）

> 2026-11-13 草案，待确认后开发。总体设计见 `docs/architecture-vnext.md`（第 7、9 节）。
> 依赖：第 2 期拆分（`docs/c2-router.md` 3.3）和沙箱第一期（`docs/sandbox-execution-design.md` 第 12 节），两者都已上线。
> 主体在**员工端本机**；服务端只多一个安全中心开关。

## 1. 要解决的问题

第 2 期已经能把「同时修这 3 个 bug」拆成 3 件，但：

- **默认一件接一件**。IT 把「同时做几件」调到 2～3 时，写操作也要全局排队、一次一个（`WriteGate`）。
  这是为了防止几件事同时改同一个工作区、互相覆盖。代价是名义上「同时做」，实际改代码还是串着来。
- **几件事改的是同一份工作副本**。改动混在一起，没法分别提交、分别评审，更没法「这件要、那件不要」。

C4 要做到：**会改代码的几件事各自在隔离的环境里同时做，各出一个任务分支 / PR，互不覆盖，员工的工作副本不被碰**。

## 2. 原则

1. **并行写只在隔离环境里**。本机工作区上的写操作仍然一次一个、照常确认（`architecture-vnext.md` 第 7 节）。
2. **沿用已有的安全边界**，不新开口子：
   - 沙箱里不确认，只因为碰不到员工电脑（不变量 3 的唯一例外）；
   - 出口只推 `flyknit/` 任务分支、不强推、不推默认分支、CI 配置默认不许改；
   - 本机 git worktree 不是沙箱，**所有确认照旧**。
3. **只用于 git 仓库**。工作区不是 git 仓库时没有分支可交回，照第 2 期的方式做（一件接一件，或同时做但写操作排队）。
4. **不自动合并**。每件做完交回分支 / PR，由员工在 GitHub 上评审合并；汇总里列出 PR，并标出可能冲突的地方。
5. **总开关默认关**（安全中心，可按部门 / 单台电脑设置）。关着时和第 2 期一模一样。

## 3. 两种隔离

| | 沙箱（Docker，已有） | 独立工作副本（git worktree，新增） |
| --- | --- | --- |
| 什么时候用 | 原对话开着「沙箱」，且 IT 允许沙箱任务 | 没有 Docker，或者没开沙箱 |
| 在哪 | 每件一个容器（沙箱第一期就是一个对话一个容器） | 每件一个 `git worktree`，放在 `%LOCALAPPDATA%\Flyknit\worktrees\` 下，**不在**员工的工作区里 |
| 分支 | 容器里切 `flyknit/<时间>-<6位>` | `git worktree add -b flyknit/<时间>-<6位>`，从员工当前分支的已提交内容开出 |
| 确认 | 容器里不确认；出口（推送、建 PR）照旧 | **全部照旧**：写文件、跑命令、推送都和平时一样问 |
| 能不能真正同时写 | 能：容器之间互不影响 | 不同 worktree 的写操作仍然**排队、一次一个**（见第 10 节问题 2） |
| 交回 | 沙箱出口：bundle 导出 → 推任务分支 → `gh pr create` | 现有的 `create_pull_request`：在 worktree 里推任务分支、建 PR，推送照常确认 |
| 员工的工作副本 | 不碰（克隆一份进容器） | 不碰（worktree 是另一个目录，共享 .git 对象） |

为什么 worktree 也值得做：很多电脑没装 Docker。worktree 虽然写操作仍然一次一个，但解决了「几件事改动混在一起」，而且每件各出一个分支 / PR。

## 4. 流程

```
员工：同时修这 3 个 bug（工作区是 git 仓库，IT 开了「隔离并行写」，同时做 ≥ 2）
  │
  ├─ 拆分建议卡：「分开做（每件在独立的沙箱 / 工作副本里，各出一个 PR）」
  │
  ├─ 员工点「分开做」
  │    ├─ 每件：开子对话 + 准备隔离环境
  │    │    ├─ 原对话开着沙箱 → 子对话也开沙箱（各自一个容器）
  │    │    └─ 否则 → 建 worktree，子对话的工作区设成这个 worktree
  │    └─ 子对话的权限不超过原对话；工作区边界就是隔离环境本身
  │
  ├─ 各件同时做（沙箱里真正并行；worktree 写操作排队）
  │    └─ 每件最后：提交 → 推任务分支 → 建 PR（沙箱走出口；worktree 照常确认）→ 接上「盯 PR」
  │
  └─ 全部结束：原对话汇总
       ├─ 每件的分支、PR 链接、CI 状态
       ├─ 改到同一个文件的几件标出来：「1 和 3 都改了 src/report.cs，合并时可能冲突」
       └─ 有最后一步（final）时照第 2 期的方式接着做，比如写一份总的变更说明
```

## 5. 安全

- **worktree 的工作区边界**：子对话的工作区就是它的 worktree 目录。
  - 「工作区内修改」权限下，写不出这个目录：员工的原工作副本、别的几件的 worktree 都在工作区外，会被权限闸门挡住或要确认；
  - 「完全权限」照现有规则处理（IT 开着工作区隔离时按「工作区内修改」算）。
- **分支**：只开 `flyknit/` 前缀的新分支，不切换、不改员工当前分支；worktree 建在员工已提交的内容上，未提交的改动不带过去（和沙箱一样）。
- **推送**：
  - 沙箱照旧走出口：只推任务分支、不强推、不推默认分支、CI 配置默认拒绝、推送时关掉仓库钩子；
  - worktree 用现有的 `create_pull_request` / `git push`，照常确认；另外加一条规则：在 worktree 里只能推它自己的 `flyknit/` 分支（单测断言）。
- **并行写闸门**：`WriteGate` 只对本机工具生效；沙箱工具（`ISandboxedTool`）在容器里执行，不排队。
- **清理**：
  - PR 合并或关闭、或者 7 天没动静后，删除 worktree（`git worktree remove`）；
  - **有未提交的改动就不删**，在任务中心提示员工；
  - 任务分支本身不删（推上去的在远端，本地的员工可以自己清）。
- **审计**：建 / 删 worktree、推送都写审计，带任务编号。

## 6. 安全中心开关（服务端，按部门 / 单台电脑）

| key | 标题 | 默认 | 说明 |
| --- | --- | --- | --- |
| `isolated_writes` | 拆开的几件在独立的沙箱 / 工作副本里各自改代码 | 关 | 需要同时打开「分开做」和「开发者工具」，且「同时做几件」≥ 2；工作区不是 git 仓库时不生效 |

沙箱沿用现有的 `sandbox_tasks` 等开关，不新增。

## 7. 代码怎么放

| 部件 | 位置 | 说明 |
| --- | --- | --- |
| `WorktreeManager` | `Flyknit.Core/Git/` | 建 / 列 / 删 worktree、开任务分支、查未提交改动，纯 git 命令，好测 |
| `ChangeOverlap` | `Flyknit.Core/Git/` | 几个分支相对起点各改了哪些文件（`git diff --name-only`），找出重叠 |
| 推送规则 | `Flyknit.Core/Git/PullRequestTools.cs` | worktree 里只能推自己的 `flyknit/` 分支 |
| `WriteGate` 豁免 | `Flyknit.Core/Agent/AgentLoop.cs` | 沙箱工具不排队 |
| 拆分接线 | `AgentHost.Router.cs` | 建组时按条件给每件准备隔离环境；汇总加分支 / PR / 重叠提示；清理任务 |
| 界面 | 拆分建议卡、汇总卡、任务中心 | 卡上写明隔离方式；汇总卡每件显示分支、PR、CI；三语 |
| 服务端 | `security_settings.py` 加一项、测试 | |

## 8. 不做的

- 远程执行节点（沙箱第二期）：电脑关机就停，和沙箱第一期一样。
- 自动合并、自动解决冲突。
- 不是 git 仓库的工作区（文档、表格）做隔离并行：没有分支可交回，照第 2 期处理。
- 只读的并行（`spawn_agent`）上限保持 3，不改。

## 9. 测试和验收

**单元测试（Core）**：
- `WorktreeManager`：在临时仓库里建两个 worktree，各改同一个文件、各自提交 → 两个分支内容互不覆盖，员工的工作副本和当前分支不变；
  分支名都是 `flyknit/` 前缀；有未提交改动时拒绝删除；删除后 `git worktree list` 里没有了。
- `ChangeOverlap`：两个分支改了同一个文件能找出来，改不同文件时为空。
- 推送规则：worktree 里推别的分支、推默认分支、强推都被拒。
- `WriteGate`：沙箱工具不排队，本机工具照旧排队。
- 拆分接线：开关关、工作区不是 git 仓库、同时做 = 1 时都不建隔离环境（和第 2 期一致）。

**真实 git**：worktree 的测试直接跑真实 git（CI 上都有）。沙箱部分沿用 `FLYKNIT_DOCKER_TESTS=1` 的端到端测试，加一条「两个容器同时改同一个仓库」。

**验收（Windows 实机）**：
1. 开了沙箱的对话里说「同时修这 3 个 bug」→ 得到 3 个 `flyknit/` 分支、3 个 PR，各自 CI 通过；汇总里列出 PR 并标出改到同一个文件的。
2. 没装 Docker 的电脑上同样一句 → 3 个 worktree、3 个分支 / PR；写操作照常问、一次一个；员工自己的工作副本 `git status` 不变。
3. PR 合并后，对应的 worktree 自动清掉；故意在一个 worktree 里留未提交的改动，它不会被删，任务中心有提示。

## 10. 需要你确认的

1. **隔离方式怎么选**：推荐**原对话开着沙箱就用沙箱**（真正并行），**否则用 worktree**；不让员工每次选。
2. **worktree 模式下写操作要不要并行**：推荐**不并行**——它还是在员工电脑上，遵守「本机写操作一次一个、照常确认」，worktree 只解决「改动混在一起」和「各出一个 PR」。
   如果你希望 worktree 也真正并行（不同目录互不覆盖），可以放开，但同时弹的确认会变多。
3. **要不要每件自动建 PR**：推荐**每件做完由 AI 用现有的建 PR 工具来建**（沙箱走出口、worktree 推送照常确认），汇总里列出来；**不自动合并**。
4. **worktree 什么时候清**：推荐**PR 合并 / 关闭后、或 7 天没动静**删除；有未提交改动不删、提示员工。
5. **开关**：推荐**新加一个 `isolated_writes`，默认关**；不新增沙箱相关的开关。
