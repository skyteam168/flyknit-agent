# 隔离执行（沙箱任务）设计

> 状态：**第一期（本机 Docker）已实现**，第二期（执行节点 + GitHub App）未开始。实现与本稿不同处见 §12。
>
> 已确认的决定：以 Docker Desktop 为准（WSL 里的 Docker / Podman 只要认 `docker` 命令也能用）；基础镜像用官方的
> `mcr.microsoft.com/devcontainers/universal:2`（工具链齐全，可用环境变量 `FLYKNIT_SANDBOX_IMAGE` 换）；
> 沙箱内网络不限制（`sandbox_network` 默认开，IT 可关成断网）；第二期用 GitHub App；
> 改 CI 配置默认不许、IT 可开（`sandbox_allow_ci_changes`）；「先出方案」默认关。
> 目标：像 Claude Code 云端版那样，长任务在隔离环境里全程不弹确认、无人值守地写代码、跑测试、建分支、提 PR；
> 员工电脑和公司系统不会因此被改坏。

---

## 1. 为什么现在做不到「不弹窗」

FlyknitBuddy 的工具在**员工自己的电脑**上执行：改的是真实工作区，命令跑在本机，推送用的是本机的 `gh`。
所以删除、覆盖、推送必须员工确认，这是 CLAUDE.md 的硬规则（不变量 3：Destructive 永不自动放行）。

Claude Code 云端版能不弹窗，靠的不是「不在用户电脑上」，而是三件事：

1. **一次性的隔离环境**：任务在新建的容器里跑，里面怎么删怎么改都只影响容器，任务结束就销毁；
2. **出口受控**：容器里没有长期凭证；能留下来的只有「推到一个新分支」和「建 PR」，并且不能推 main、不能强推；
3. **人审合并**：PR 合不合由人决定，CI 和评审照常把关。

本设计在 FlyknitBuddy 里补上这三件事。

## 2. 目标与非目标

**目标**

- 员工（主要是 IT 和程序员）可以把一件开发任务交给「沙箱任务」：AI 在隔离环境里拉代码、改代码、装依赖、跑测试、提交，
  全程不弹确认；做完推到一个新分支并建 PR，接着按现有的「盯 PR」规则跟进 CI。
- 两种隔离环境，同一套接口：
  - **B. 本机沙箱**（第一期）：在员工电脑上用 Docker Desktop 或 WSL 起一次性容器；
  - **A. 执行节点**（第二期）：公司服务器上的独立服务起容器，员工关机也能接着跑。
- 安全线不降：GitHub 令牌不进容器；推送只能到新分支；对外操作有白名单；全程审计；IT 有总开关。

**非目标**

- 不替代现有的本机办事模式。办公类任务（Excel、文件整理、ERP 网页）照旧在本机做，照旧要确认。
- 不在沙箱里操作员工电脑上的文件、软件、浏览器登录态。沙箱只拿到一份仓库拷贝。
- 不做 Windows 容器。沙箱统一是 Linux 容器，开发工具链按 Linux 走。
- 第一期不支持 GitLab / Gitee（接口留好，出口代理按主机扩展）。

## 3. 总体架构

```
                         ┌───────────── 服务端（FastAPI，网关 / 策略 / 审计，不变）─────────────┐
                         │  /chat/completions（沙箱任务也走这里，按设备 + 场景计量）               │
                         │  沙箱任务登记、配额、审计（新）    GitHub App 配置（A，新）              │
                         └──────────────▲───────────────────────────────▲────────────────────────┘
                                        │ 设备 Token                     │ 执行节点 Token（A）
 ┌──────────── 员工电脑 ───────────────┐ │                    ┌──────────┴──────── 执行节点（A，新服务）────────┐
 │ AgentLoop（办事模式，不变）          │ │                    │ 任务队列 → 每任务一个容器                      │
 │ SandboxTask（新）                   │─┘                    │ Headless AgentLoop（复用 Flyknit.Core，Linux）  │
 │   ├─ ISandbox（统一接口）            │                      │ 出口代理：推分支、建 PR（持 GitHub 令牌）        │
 │   │    ├─ DockerSandbox（B）        │                      └─────────────────────────────────────────────────┘
 │   │    └─ RemoteSandbox（A，调执行节点）
 │   └─ EgressBroker（B：本机出口代理，用员工的 gh 登录）
 └─────────────────────────────────────┘
```

核心是 Core 里一个新接口 `ISandbox`：

| 方法 | 作用 |
| --- | --- |
| `PrepareAsync(repo, baseRef)` | 起容器，在容器里克隆仓库（或从员工的本地仓库导入一份），建任务分支 `flyknit/<任务号>-<简称>` |
| `ExecAsync(command, cwd, timeout)` | 在容器里执行命令（`docker exec` / 执行节点 API），返回输出 |
| `ReadFile / WriteFile / List / Search` | 在容器的仓库目录里读写，路径限定在仓库内 |
| `ExportBranchAsync()` | 把任务分支导出成 git bundle，交给出口代理 |
| `DisposeAsync()` | 销毁容器和卷 |

沙箱任务里的工具（`read_file`、`write_file`、`edit_file`、`multi_edit`、`grep`、`run_shell`、`git_*`）都换成「沙箱版」实现：
同样的工具名和参数，模型不用学新东西，执行落到 `ISandbox` 上。

## 4. 安全模型

### 4.1 新增「沙箱」权限档

| 操作 | 本机办事（现状） | 沙箱任务（新） |
| --- | --- | --- |
| 读、搜索、只读命令 | 自动 | 自动 |
| 改文件、普通命令、装依赖、跑测试 | 按权限模式，多数要确认 | **自动**（只影响容器） |
| 删除、覆盖、`git reset --hard` 等容器内的 Destructive | 永远逐次确认 | **自动**（容器销毁即还原，影响不出容器） |
| 推送 | 确认 | 只能经出口代理推**任务分支**，自动；推 main / 默认分支 / 强推 / 删分支：**拒绝** |
| 建 PR | 确认 | 经出口代理，自动（PR 仍要人审合并） |
| 删仓库、改仓库设置、`secret`、`gh auth`、发版本 | 永远逐次确认 | **拒绝**（沙箱里根本没有凭证，出口代理也不提供） |
| 访问网络 | 按网络白名单 | 只能访问白名单：包管理源（经公司镜像）、GitHub（只读拉取）、IT 加的地址 |

这需要修订 CLAUDE.md 不变量 3，改成：
「Destructive 永不自动放行；**例外：沙箱档内、影响限定在一次性容器里的操作。对外的效果（推送、建 PR、网络请求）仍按出口规则判定，不因沙箱放宽。**」

`CommandAnalyzer` 和 `blocked_patterns` 在沙箱里照样跑。被拦下的命令不会弹窗，直接按「被策略阻止」返回给 AI，
防止有人借沙箱去打公司内网。

### 4.2 令牌不进容器（出口代理）

- 容器里**没有** GitHub 令牌，也没有设备 Token。拉代码用只读方式（见 §6），推送和建 PR 都交给容器外的出口代理。
- 出口代理的流程：
  1. 从沙箱导出任务分支（git bundle）；
  2. 导入一个代理自己的裸仓库，导入时关掉所有 hooks（`core.hooksPath` 指向空目录），防止仓库里的钩子在容器外执行；
  3. 检查：分支名必须是 `flyknit/…`；不能是默认分支；不能强推（远端已有这个分支、且不是快进时拒绝）；
     本次改动的文件数、大小有上限；不能包含 `.github/workflows` 的改动，除非 IT 开了「允许改 CI 配置」；
  4. 推送，再用 `gh pr create` 或 GitHub API 建 PR；
  5. 记审计：哪个员工、哪个任务、推了哪些提交、PR 地址。
- 这样即使 AI 被仓库里的恶意内容诱导（提示词注入），它在容器里也拿不到令牌，推不了别的分支，删不了仓库。

### 4.3 资源和预算

- 每个容器限制 CPU、内存、磁盘，并设总时长（默认 2 小时，IT 可调）。
- token 预算沿用 `RunBudget`，沙箱任务按长任务算；每台设备、每天的沙箱任务数由服务端限额。
- 网络限制：B 用 Docker 自定义网络加本机的出站代理（只放行白名单主机）；A 用执行节点所在网络的出站策略。

### 4.4 审计

- 容器里每条命令、每次文件改动，都按现有审计格式记录，`actor = sandbox`，带任务号。
- 服务端记录沙箱任务的登记、结束、推送和 PR。
- 员工可以在任务页看完整执行链路，下载容器日志。

## 5. 两种隔离环境

### 5.1 B：本机沙箱（第一期）

- **前提**：员工电脑装了 Docker Desktop（WSL2 后端），或者 WSL 里装了 Docker / Podman。
  客户端启动时检测 `docker version`，检测不到就不显示「沙箱任务」。
- **镜像**：IT 在后台配置基础镜像（默认带 git、Node、Python、.NET SDK 的开发镜像），经公司镜像仓库拉取。
  仓库里有 `.flyknit/sandbox.json`（或 devcontainer）时，按它装依赖。
- **代码从哪来**：
  - 员工当前工作区是 git 仓库时，从本地仓库 `git clone --no-hardlinks` 一份到 Docker 卷。
    员工的工作副本不会被碰，已提交但未推送的提交也能带上；
  - 也可以直接给一个 GitHub 仓库地址。容器里没有令牌，私有仓库由出口代理在宿主上拉好，再以 bundle 导入。
- **AgentLoop 在哪跑**：在员工电脑的 FlyknitBuddy 里（和现在一样），只是工具换成沙箱版。
  所以要求电脑开着；程序被关，按现有断点续跑。
- **出口代理**：在 FlyknitBuddy 宿主里，用员工自己的 `gh` 登录推送和建 PR。令牌只在宿主进程里，不进容器。
- **优点**：不需要新服务器；开发者电脑现成就能用；第一期就能交付。
- **局限**：占用员工电脑资源；关机就停；Docker Desktop 的商用授权由公司按实际情况处理。

### 5.2 A：执行节点（第二期）

- **新服务** `runner/`：独立部署，和网关分开，可以多台。用 .NET 8 写在 Linux 上，直接复用 `Flyknit.Core` 的 AgentLoop 和工具，
  不重写第二套 Agent。
- **任务从哪来**：员工端、手机端、定时任务把「沙箱任务」提交给服务端，服务端派给空闲的执行节点。
  执行节点用自己的令牌调网关，用量记在发起员工的设备上，并写入任务授权记录（`task_grants`，来源 `sandbox`）。
- **AgentLoop 在执行节点上跑**：员工关机也能接着做；进度经服务端推回员工端和手机（复用 `task.*` 事件）。
- **人工确认**：沙箱里没有需要确认的操作。确实需要员工拍板的（例如「要改 CI 配置吗」），AI 用 `ask_user` 发到员工端或手机，
  等回答期间任务挂起，超时就把问题写进 PR 说明。
- **GitHub 授权**：IT 在公司 GitHub 组织里装一个 GitHub App，员工在 FlyknitBuddy 里授权一次（用户授权令牌，加密存在服务端）。
  执行节点每个任务申请一个短期令牌，只给这一个仓库的 `contents:write` 和 `pull_requests:write`，1 小时过期；
  只由出口代理使用，不进容器。提交和 PR 显示「员工本人 via FlyknitBuddy」。
- **对 CLAUDE.md 分工的影响**：服务端（网关）仍然不执行命令；执行命令的是新的执行节点，单独部署、单独授权。
  §1 的分工表要加一行「执行节点」：负责在隔离容器里跑沙箱任务；不负责操作员工电脑、不持有模型 Key。

## 6. 和现有功能的关系

| 现有功能 | 沙箱任务里怎么用 |
| --- | --- |
| 开发者工具（grep / multi_edit / git_*） | 换成沙箱版，名字和参数不变 |
| 子代理 spawn_agent | 可用；子代理和主任务共用同一个容器 |
| 派遣专家 | 第一期不可用（专家可能连业务系统，不进沙箱） |
| MCP 连接器 | 第一期不可用（连接器连的是公司系统，属于对外操作）；以后按「沙箱可用」标记逐个放开 |
| 技能 | 可用（只读加载说明；技能脚本在容器里跑） |
| 盯 PR | 沿用。B 由员工端盯，A 由执行节点盯；CI 失败的自动修复在新的沙箱任务里做，同样不弹窗 |
| 断点续跑 | B 沿用本机断点；A 由执行节点存断点 |
| 计划模式 | 沙箱任务默认先出方案、员工点「开始」后进入无人值守（可在后台改成直接开始） |

## 7. 界面

- 输入框的模式里新增「沙箱任务」（开发者工具和沙箱开关都开着才显示），选择仓库、基准分支，可选「先出方案」。
- 任务卡片显示：隔离环境（本机 Docker / 执行节点）、任务分支、进度、用时和 token、最后的 PR 链接。
- 右侧「终端」显示容器里的命令输出；「文件」显示容器里的仓库，只读浏览。
- 任务结束后：PR 链接、改动摘要、测试结果；「再改一轮」会在新容器里接着改同一个分支。

## 8. 服务端和管理后台

- 安全中心新增（默认关闭、锁定）：
  - `sandbox_tasks`：允许沙箱任务；
  - `sandbox_backend`：`local` / `runner` / `both`；
  - `sandbox_allow_ci_changes`：允许改 CI 配置（默认关）；
  - 网络白名单、基础镜像、资源上限、每日任务数。
- 新表（只加不删）：
  - `sandbox_tasks`：任务、发起人、仓库、分支、状态、预算、PR；
  - `runner_nodes`：执行节点（A）；
  - `github_app` 配置和员工授权（A，令牌加密存储）。
- 网关不变。沙箱任务的模型调用带 `flyknit_source = sandbox`，用量单独统计。

## 9. 分阶段计划

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| S1 本机沙箱基础 | `ISandbox` + `DockerSandbox`；沙箱版文件 / 命令 / git 工具；沙箱权限档；Docker 检测；开关 | 在装了 Docker Desktop 的 Windows 上：克隆仓库、改代码、跑测试，全程不弹窗；容器里的 Destructive 自动执行且不影响宿主；单测覆盖权限档 |
| S2 出口代理 | 本机出口代理：bundle 导入、关 hooks、分支和强推检查、建 PR、审计；沙箱任务接上盯 PR | 推 main、强推、改 workflows 都被拒绝；正常任务自动建 PR 并开始盯 CI |
| S3 网络与资源 | 出站白名单代理、资源上限、总时长、每日限额；界面任务卡片 | 容器访问白名单外地址失败；超时任务被结束并清理 |
| S4 执行节点（A） | `runner/` 服务、任务派发、GitHub App、执行节点上的 headless AgentLoop、进度回推、手机发起 | 员工关机后任务继续，完成后手机收到 PR 链接 |
| S5 扩展 | MCP「沙箱可用」标记、GitLab / Gitee 出口、devcontainer 支持 | 按需 |

每个阶段单独提 PR，补测试；安全相关（权限档、出口检查）不能只改代码不补测试。

## 11. 风险

| 风险 | 应对 |
| --- | --- |
| 提示词注入诱导 AI 外泄代码或令牌 | 容器里没有令牌；网络白名单；出口只认任务分支 |
| 仓库里的 git hooks、构建脚本在宿主上执行 | 宿主侧只用关了 hooks 的裸仓库导入导出，不在宿主上跑构建 |
| 容器逃逸 | 不用特权模式、不挂 Docker socket、只读根文件系统，加 seccomp 默认配置；执行节点按不可信负载隔离部署 |
| 员工电脑资源被占满 | 资源上限、同时只跑一个沙箱任务（可调） |
| 无人值守任务烧 token | 长任务预算、每日限额、总时长上限 |
| Docker Desktop 授权 | 公司按规模评估；也可以改用 WSL 里的开源 Docker / Podman |

## 12. 第一期实现说明（与上文的差异如实列出）

**做了什么**

- `Flyknit.Core/Sandbox/DockerSandbox.cs`：宿主上 `git clone`（不带员工本机未提交的改动和未跟踪文件）→ `docker create`（带 `flyknit.sandbox` 等标签，
  `--cpus` / `--memory` / `--pids-limit 4096` / `no-new-privileges`，不挂任何宿主目录、不挂 Docker socket）→ `docker cp` 进容器 →
  在容器里切出任务分支 `flyknit/<日期-时间>-<6位>`。一个对话一个容器，程序重启后按标签找回；启动时清理没人用的容器。
- `SandboxTools.cs`：`read_file` `list_dir` `search_files` `grep` `write_file` `edit_file` `multi_edit` `delete_path` `run_shell` `git_*`
  同名替换成在容器里执行的版本，都实现 `ISandboxedTool`，不弹确认；`blocked_patterns` 照拦。本机终端、浏览器、连接器、`open_app` 这一轮不注册。
- `SandboxEgress.cs`（出口）：从容器导出 bundle → 员工电脑临时裸仓库（`core.hooksPath` 指向空目录）→ 只认任务分支、不推默认分支、
  refspec 不带 `+`（不强推）、改动文件 ≤ 2000、CI 配置默认拒绝 → 用员工本机的 git 凭证推送 → `gh pr create --repo` → 接上「盯 PR」。
- 提示词注入：沙箱工具不受污染模式影响（反正只影响容器），出口在读到疑似注入后照样要员工确认。
- 安全中心：`sandbox_tasks`（默认关、锁定）、`sandbox_network`（默认开）、`sandbox_allow_ci_changes`（默认关）、`sandbox_cpus`（4）、`sandbox_memory_gb`（8）。
- 界面：输入框下方「沙箱」开关（IT 打开两个开关后才显示；关闭时确认，会删容器），「文件」标签的仓库面板显示沙箱状态和任务分支。

**和设计稿不一样 / 还没做的**

- 容器里以 root 运行（便于装依赖），没有做只读根文件系统和自定义 seccomp（用 Docker 默认配置）。
- 网络按确认结果不限制，没有出站白名单代理（S3 的白名单部分不做；IT 可整体断网）。
- 没有沙箱任务的总时长上限和单独的每日限额，沿用长任务预算和网关配额。
- 出口只写本机日志，没有单独上报审计事件。
- 基础镜像还不能在管理后台配置，只能用环境变量 `FLYKNIT_SANDBOX_IMAGE`。
- 只支持 GitHub 远端。
