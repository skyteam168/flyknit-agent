# 方案：减少不必要的确认（审批 P0 + 合并确认）

> 2026-11-13 定稿：第 9 节五个问题都按推荐。实施顺序见第 10 节（PR 1 = 改动一、二）。来源：员工反馈「要点的确认太多，派遣专家时每一步读取都要授权」，
> 以及对 Claude Code / Codex / Gemini CLI / Cline / Goose 审批设计的对照分析（结论见第 1 节）。
> 范围只有五件事：修两个缺陷、派遣时一次授权、后台标只读工具、同一步的确认合成一张。
> **不降低任何安全线**：高危永不自动、污染模式、IT 的 confirm 规则、网络白名单、闸门顺序全部不动。

## 1. 为什么

行业共识是：只读不问、工作区内编辑不问、其余靠沙箱圈住；人工确认只留给「越界」和「不可逆」，
而且**一次同意要覆盖到「这次任务里的这一类」**。Anthropic 的数据：93% 的确认被直接点了同意，形成「审批疲劳」，
确认多了反而不安全。

我们的分级本身不松也不过严（只读、工作区内写都已自动），确认多主要来自下面这些，前三条已在代码里核实：

| # | 原因 | 位置 | 后果 |
| --- | --- | --- | --- |
| ① | 「本任务内不再询问」按 `工具名:摘要第一个词` 记；MCP 的摘要是「参数名：参数值」 | `AgentLoop.cs` `SessionApprovalKey`、`McpTool.Describe` | 每次查询的键都不同，点了等于没点 |
| ② | 会话授权存在每个 `AgentLoop` 自己的 `_sessionApprovals` 里 | `ExpertDispatcher.cs`、`SpawnAgentTool.cs` 都新建循环 | 主助手那边点过的，专家、子代理还要再点；派 3 个专家点 3 遍 |
| ③ | MCP 工具只认对方声明的 `readOnlyHint`，很多厂商不写 | `McpClient.cs`、`McpTool.Assess` | 查询类工具每次确认；只读专家用它直接被拦下 |
| ④ | 一步里模型发了好几个要确认的调用，是一个一个弹的 | `AgentLoop` 逐个 `PrepareCallAsync` | 同一件事被打断好几次 |

## 2. 原则

1. **只改「问几次」，不改「问不问」**。凡是现在要确认的，改完后员工仍然至少看到一次、点一次。
2. **不碰红线**：
   - 高危（Destructive）永不进会话授权、不进派遣授权、不进「全部允许」；
   - `AlwaysAsk`（污染模式、IT 的 confirm 规则）照旧每次单独问；
   - `blocked_patterns` → `CommandAnalyzer` → `PermissionMode` + 工作区 → `ApprovalStore` 的顺序不变。
3. **专家只做减法**：专家能沿用的只是员工本人已经给过的授权，不会因此多出工具或权限；
   专家的 `disallowed_tools`、`mcp_servers`、`read_only` 照旧生效。
4. **放宽只能由服务端下发**：标只读工具是管理员在后台做，员工不能自己标。
5. **向后兼容**：老界面、命令行、ACP、手机端收不到新消息类型时退回现在的逐条确认。

## 3. 改动一：会话授权按规则记（修 ①）

**现在**：键 = `工具名:` + 摘要第一个词（`npm`/`git`/`pip`… 取两个词）。

**改成**：

- 判定里带了规则候选（`decision.Rule` 不为空），键就用规则：`{Rule.Tool}:{Rule.Prefix}@{Rule.Scope}`。
  - MCP：`Rule.Prefix` = 工具名，和「以后自动」同一个粒度——允许过「MES · 查询工单」，这次任务里所有查询工单都不再问，别的工具照问。
  - `run_shell`：`Rule.Prefix` 来自 `CommandAnalyzer.SuggestRulePrefix`，范围带工作区。
- 没有规则候选的（解释器 `python x.py`、网址看不出来的联网命令等），**退回现在的算法**，行为不变。
- 高危、`AlwaysAsk` 照旧不进会话授权。

**测试**（`SessionApprovalTests`）：

- MCP 不同参数连调两次，第二次不问；
- 换一个 MCP 工具照问；
- 高危同前缀照问；
- 污染后照问；
- `python a.py` 允许后 `python b.py` 的行为和现在一致。

## 4. 改动二：同一个任务里共用会话授权（修 ②）

- Core 新增 `SessionApprovals`（线程安全的集合），`AgentLoop` 通过属性注入，没注入时自己 new 一个，行为和现在一样。
- **一次办事运行一份**：`AgentHost.RunAsync` 建一份，经 `ToolContext.SessionApprovals` 传下去：
  - `ExpertDispatcher` 和 `SpawnAgentTool` 建循环时用父任务那份；
  - 专家卡片上点「本任务内不再询问」也记进这一份，主助手和别的专家都能沿用。同一个员工、同一个任务，没有越权问题。
- **不跨任务**：C2 拆开的几件是不同任务，各用各的；任务结束就丢弃，和现在一样。
- **派遣授权（第 5 节）是子层**：只在这位专家这次派遣里有效，不往上传。
- 审计不变：用会话授权放行的照旧记 `decision = session`。

**测试**：

- 主助手允许后派出的专家不再问；
- 专家允许后主助手不再问；
- 两个拆开的任务互不影响；
- 专家被禁用的工具不会因为共用而能用；
- 高危照问。

## 5. 改动三：派遣时一次授权

**什么时候出卡**：派遣一位专家，它这次能用的工具里有「要确认、但不是高危」的 MCP 工具时，在专家开工前出一张卡。只算以下工具：

- 对方没声明只读，也没被管理员标只读；
- 没声明 `destructiveHint`；
- 不命中 IT 的 confirm 规则；
- 员工还没有「以后自动」或本任务授权过。

卡片内容：

> **MES 生产分析专家** 这次可能要用：MES · 查询工单、MES · 查询产量、ERP · 查询库存（共 3 个）
> [这次派遣内都直接执行] [用到时逐条问我]

- 选「都直接执行」：这几个工具记进这次派遣的子层授权，专家跑完就失效。
- 选「逐条问我」或关掉卡片：和现在一样；**不取消派遣**。
- 这张卡只覆盖列出来的 MCP 工具。专家要跑的命令、写工作区外的文件、高危操作，照旧到时候单独问。
- 污染模式下照旧逐条问：`AlwaysAsk` 优先于一切授权。
- 只读专家：现在遇到要确认的操作直接拦下。这次**不改**这条规则；它用的查询工具靠第 6 节标成只读后就能自动用。
- 命令行 `-p`：这张卡按现有规则处理（默认拒），等于逐条问，逐条也拒，行为不变。
- 手机端：退回为一条普通审批，文字里列出工具名。

**实现**：

- 卡片走现有 `tool.confirm` 消息，加可选字段 `bundle: [{ tool, label }]`，老界面会忽略这个字段；
- 宿主在 `ExpertDispatcher.RunAsync` 建循环前调用一次 `IConfirmationHandler.ConfirmAsync`；
- `actor` 填这位专家；
- 卡片上的选项：`allowForSession` = 都直接执行，其余 = 逐条问。

**测试**（`DelegationTests`）：

- 有候选工具才出卡；
- 选「都直接执行」后这些工具不再问，别的工具照问；
- 高危、confirm 规则命中的不在清单里；
- 派遣结束授权失效；
- 选「逐条问」后行为和现在一致；
- 污染后照问。

## 6. 改动四：后台标「只读工具」（修 ③）

**服务端**：

- `McpVendor` 加列 `readonly_tools`（JSON，默认 `[]`，只加不删）；
- 管理端读写接口带上这一列；
- 员工端拉连接器配置时下发；
- 按部门的使用范围过滤照旧。

**后台**：连接器编辑页加「只读工具」一栏：

- HTTP 连接器点「测试连接」后，把对方返回的工具列成复选框；
- stdio 连接器服务端探测不到工具，手填工具名；
- 文案提示「只勾查询类，勾了的工具员工端不再确认」。

**员工端**：`McpTool.Assess` 增加一种情况：

- 工具在 `readonly_tools` 里，**且**对方没声明 `destructiveHint` → 自动执行，原因写「管理员标为只读」；
- 对方声明了 `destructiveHint` 的，标了也不生效，照旧每次问；后台在这种工具旁边标出来，说明为什么不生效；
- 标只读的工具也可以和相邻的只读调用同时跑（`CanRunInParallel`），和对方自己声明只读的一样。

**审计**：后台改这一栏写管理审计。

**测试**：

- 服务端：默认空、保存后读回、员工端配置里有、部门范围外不下发；
- Core：标了的自动执行；声明 destructive 的标了无效；没标的照旧要确认；只读专家能用标了的工具。

## 7. 改动五：同一步的确认合成一张（修 ④）

**现在**：一步里的工具调用按顺序一个接一个「判定 → 确认 → 执行」，第二张卡要等第一个执行完才弹出来。

**改成**：

1. 一步里有 ≥ 2 个调用时，先把它们全部**预判**一遍。预判和现在的判定完全相同（工具判定 → IT 规则 → 污染 → 长期规则 → 会话授权），只是不执行。
2. 需要问人的 ≥ 2 个时，弹**一张合并卡**，逐项列出摘要、原因和类型：
   - 「全部允许」只勾普通项；
   - **高危和 `AlwaysAsk` 的项默认不勾，要员工逐个勾**；
   - 每项也可以单独拒绝；
   - 底部有一个「本任务内同类不再询问」，只对能进会话授权的项生效。
3. 然后照旧按顺序逐个执行。**执行前再判定一次**：判定变严了（比如前一个调用的结果触发了污染模式、类型变了），这一项作废合并卡的答案，单独再问。
4. 只需问 1 个时和现在完全一样。

**接口**：

- `IConfirmationHandler` 加 `ConfirmBatchAsync`，默认实现是逐个调用 `ConfirmAsync`，所以命令行、ACP、手机端、专家子任务的包装都不用改，自动退回逐条；
- 桌面端 `WebBridge` 实现合并卡：
  - 新消息 `tool.confirmBatch { requestId, conversationId, items: [{ callId, summary, reason, effect, mustTick, rememberable }], actor? }`；
  - 回复 `tool.confirmBatch { requestId, allowed: [callId], session: bool }`；
  - 拒绝的项照旧写「用户拒绝了这个操作」。
- C2 拆分的「同组合并确认」不受影响。它是跨对话的合并，这次是同一步内的合并，两者可以同时存在。

**界面**：

- `ConfirmBar.vue` 加合并卡的展示；
- 三语文案；
- `mockHost` 能模拟一次合并确认。

**测试**（`AgentLoopTests`）：

- 两个要确认的调用只问一次；
- 一个高危一个普通时，「全部允许」不放行高危；
- 第一个调用的结果触发污染后，第二个重新问；
- 只有一个要问时走老路；
- 拒绝的项有合法结果，上下文完整；
- 默认实现逐条，行为和现在一致。

## 8. 不做的

- 不做「全部放行 / YOLO」，不做模型判断替人放行（「智能放行」）。等有了确认通过率的数据再说。
- 不放宽解释器（`python x.py`）。要从根上解决得靠 Windows 轻量沙箱，单独立项。
- 不改长期规则（「以后自动」）的能力范围。
- 后台的「确认通过率」统计这次不做，下一期再做。

## 9. 需要你确认的

1. **会话授权共用到多大**：推荐「一次办事运行」——主助手加它派出的专家、子代理共用，任务结束失效，不跨 C2 拆开的任务。
   另一种是整个对话共用，范围更大，不推荐。
2. **派遣时一次授权的卡片什么时候出**：推荐只在有第 5 节那类候选工具时出，没有就不打扰，并且不设默认按钮。
   另一种是每次派遣非只读专家都出一张，会多一次打扰。
3. **只读工具谁来标**：推荐只有管理员在后台标；员工端不提供这个入口。
4. **合并卡上的高危项**：推荐默认不勾、必须逐个勾，「全部允许」不包括它们。
   另一种是高危不进合并卡、照旧单独弹，更保守，但又多一次打断。
5. **合并卡做到哪些端**：推荐桌面端做，命令行 / ACP / 手机端先退回逐条（ACP 协议本来就是一次一个），之后看反馈再说。

## 10. 估算和拆分

建议拆成三个 PR，按顺序：

| PR | 内容 | 主要改动 | 估算 |
| --- | --- | --- | --- |
| 1 | 改动一 + 二（修缺陷） | Core：`AgentLoop`、`SessionApprovals`、`ExpertDispatcher`、`SpawnAgentTool`；宿主：`AgentHost`；测试 | 小 |
| 2 | 改动四（后台标只读） | 服务端 model / 迁移 / schema / 接口；admin 连接器页；Core：`McpTool`；测试 | 小～中 |
| 3 | 改动三 + 五（派遣授权、合并卡） | Core：`ExpertDispatcher`、`AgentLoop` 预判与 `ConfirmBatchAsync`；`WebBridge`；web：`ConfirmBar`、types、i18n、mockHost；测试 | 中 |

每个 PR：

- 跑 Core 全量测试，以及服务端相关测试；
- 跑 web / admin / site 的构建；
- 跑 Flyknit.Client 的语法检查；
- 帮助中心更新 `site/guide/safety.md`、`experts.md`、`connectors.md` 和 `site/admin/security-center.md`；
- 最后由你在 Windows 实机上验收：派一位用 MCP 查询的专家，点击次数应明显减少；高危操作照旧逐条确认。
