# 方案：VNext 第 3 期——Watchdog（backlog C3）

> 2026-11-13 草案，待确认后开发。总体设计见 `docs/architecture-vnext.md`（第 4、5、8 节）；依赖第 1 期的任务账本（`docs/c1-unified-tasks.md`）。
> 主体在**员工端本机**；服务端只加一个用途标签、一个心跳字段和三个安全中心开关。

## 1. 要解决的问题

现在防「空转」只有 `LoopGuard`（`Flyknit.Core/Agent/LoopGuard.cs`）。它在一轮 `AgentLoop` 里面，按规则看最近的工具调用：

| 能抓到的 | 怎么判断 |
| --- | --- |
| 原地打转 | 同一个调用、结果也一样：3 次提醒，5 次停 |
| 轮询等待 | 同一个调用、结果在变：4 次提醒，8 次停 |
| 反复改同一个文件 | 按路径计数：4 次提醒，8 次停 |
| 只更新计划不干活 | 连续 3 次提醒，5 次停 |

它看不到的：

1. **换着花样空转**。每次调用都不一样（读这个文件、搜那个词、再列一个目录……），规则认不出来，但几十步下来计划一步没推进、什么都没产出。长任务模式下步数上限放宽、到上限还自动续跑，这种情况最费 token。
2. **跑偏**。一直在做事，但做的不是员工要的（让整理报表，却在修 Excel 的格式问题修了半小时）。
3. **跨轮**。`LoopGuard` 每轮重新计数；长任务自动续跑、中断续跑后，前面空转的账就清零了。
4. **程序不在了**。员工电脑关机、断网、程序崩溃时，手机端和后台看不出「这台电脑上还有任务在跑」，只能干等。

## 2. 原则

1. **先程序、后模型**。程序信号（有没有新操作、计划推进、产出文件）每分钟算一次，不花 token；只有程序判断「可疑」时，才请便宜模型看一眼。
2. **宁可漏判，不误伤**。正在跑的长命令（编译、跑测试、装软件）、等员工确认、等员工回答、暂停中，一律不算没进展。自动停下要**程序和模型都认定**，而且是**提醒过之后**仍没改善。
3. **停下走正常的停止路径**：和员工点「停止」一样，已发出的工具调用补合法结果，写审计，任务账本记原因（不变量 4）。
4. **不放宽任何东西**。Watchdog 只会提醒和停止，不会批准、不会重试、不会改权限。
5. **数据最少**。给模型看的只有任务目标、计划、最近操作的摘要；工具输出只取开头一小段，并先过 `SecretRedactor`。心跳上报不带任务标题和内容。
6. **总开关默认关**（安全中心，可按部门 / 单台电脑设置）。关着时行为和现在完全一样。

## 3. 三层检查

```
每一步（已有）      LoopGuard：规则，进程内，当场提醒 / 停
每分钟（新增）      进展信号：程序判断，不花 token        ──可疑──┐
可疑时（新增）      模型判断：便宜模型，看目标 + 计划 + 最近操作 ◄─┘
                     ├─ 有进展 → 不打扰，过一阵再看
                     ├─ 卡住 / 跑偏（第一次）→ 提醒 AI + 通知员工
                     └─ 提醒后仍卡住 / 跑偏 → 自动停下（开关打开时），否则再通知一次
```

### 3.1 进展信号（程序，每分钟）

宿主给每个正在跑的任务记一份 `ProgressSignals`（只在内存里，跟着任务走、跨轮不清零）：

| 信号 | 来源 | 算进展吗 |
| --- | --- | --- |
| 新的操作 | `LoopGuard.LastWasNew`（这一轮没做过一模一样的调用） | 算，但只读类操作（`read_file` `list_dir` `search_files` `grep` 等）**连续**很多次后降权：只看不做超过 15 次不再算 |
| 计划推进 | `update_plan` 里完成的步数增加 | 算（最强的信号） |
| 产出 / 改动 | `ToolResult.Outputs`、`RecordChange`（新建、修改文件） | 算 |
| 回答员工 | 模型输出了正文（不是纯工具调用） | 算 |
| 正在执行的工具 | 工具已发出、还没回来（`run_shell` 编译 / 测试） | **暂停计时**：不算进展，也不算没进展 |
| 后台命令有新输出 | `shell_output` 返回的新输出 | 算 |
| 等员工 | 等确认、`ask_user`、暂停 | **暂停计时** |

**可疑**：在不暂停计时的时间里，连续 **N 分钟**（默认 10，长任务模式 ×2）没有任何算进展的信号，**并且**这段时间里至少走了 8 步。也就是「一直在动但没进展」。只是慢（每一步都很久）不算可疑。

### 3.2 模型判断（可疑时才调）

- **场景**：`title`（便宜模型，后台已经配好，不用新配；见第 10 节问题 2）。**用途**记成 `watchdog`，后台「按用途」能看到花了多少。
- **给模型看的**（总共控制在约 2k token）：
  - 任务目标：这件事第一句话的前 300 字；
  - 当前计划和完成情况；
  - 最近 20 步的操作摘要：工具名 + 关键参数（路径、命令前 80 字）+ 结果开头 120 字；
  - 已经用了多少步、多少时间、多少 token。
  - 全部先过 `SecretRedactor`，不带附件、图片、记忆。
- **要它回答**（JSON）：`{"verdict": "progressing|stalled|drifting", "reason": "一句话", "advice": "给 AI 的一句建议"}`。解析不了按 `progressing` 处理（宁可漏判）。
- **频率上限**：同一个任务两次判断之间至少隔 5 分钟；一个任务最多判断 6 次。
- **模型调用失败**（离线、配额用完）：只按程序信号提醒，**不自动停**。

### 3.3 处理

| 情况 | 做什么 |
| --- | --- |
| `progressing` | 什么都不做，计时重新开始 |
| 第一次 `stalled` / `drifting` | ① 在下一个工具结果后面附一段【系统提醒】给 AI（和 `LoopGuard` 的提醒同一个位置），内容带上模型给的建议；② 通知员工：系统通知 + 任务中心卡片上标「可能卡住了：原因」，带「停止」「不用管」两个按钮；③ 写一条审计 |
| 员工点「不用管」 | 这个任务后面不再提醒（直到员工自己再说话开新任务） |
| 提醒后又过了 N 分钟，程序仍判可疑、模型仍判 `stalled` / `drifting` | 「自动停止」开着：走正常停止，任务记成失败，原因「看门狗：长时间没有进展」或「看门狗：偏离了目标」，通知员工并写审计；关着：再通知一次，不停 |
| 远程来的任务（手机 / 钉钉 / 企业微信） | 提醒和停止的结果照现在的方式回给发起人 |

## 4. 服务端：心跳

现在员工端只要和服务端说话（任何带设备 Token 的请求）就会刷新 `devices.last_seen`；配置每 10 分钟拉一次。但服务端不知道这台电脑上**有没有任务在跑**。

- 员工端在**有任务在跑时**每 2 分钟发一次心跳 `POST /api/v1/client/heartbeat`，只带：正在跑的任务个数、各自的来源（`ui` / `mobile` / `schedule`……）、任务编号。**不带标题和内容**（标题可能就是聊天内容，共享管理 token 不能看聊天正文）。没任务时不发，靠原来的 `last_seen`。
- 服务端在 `devices` 上加两列（只加不删、有默认值）：`running_tasks`（JSON，最多 20 条）、`heartbeat_at`。
- **判定失联**：有任务在跑、但超过 10 分钟没心跳。
  - 后台「设备」列表：显示「进行中 N 个任务」；失联的标红「失联（有任务在跑）」。
  - 手机端：给绑定电脑发的任务，电脑失联时把进度显示成「电脑已离线」（手机通道本来就知道 WS 连没连着，这里补上「连着但任务没动静」的情况）。
- 服务端**不会**替员工端停任务，也拿不到任务细节（不变量：执行和细节都在本机）。

## 5. 安全中心开关（服务端，按部门 / 单台电脑）

| key | 标题 | 默认 | 说明 |
| --- | --- | --- | --- |
| `watchdog` | 看门狗：检查任务有没有进展 | 关 | 关着时只有原来的 `LoopGuard` |
| `watchdog_auto_stop` | 看门狗：提醒后仍没进展就自动停下 | 关 | 打开 `watchdog` 后才有意义；关着时只提醒、通知 |
| `watchdog_minutes` | 多久没进展算可疑（分钟） | 10 | 5～60；长任务模式自动 ×2 |

三项都进 `test_security_rules.py` 的清单和 `SecuritySwitchTests.EverySwitchWeShipIsActuallyRead`。

## 6. 代码怎么放

| 部件 | 位置 | 说明 |
| --- | --- | --- |
| `ProgressSignals` | `Flyknit.Core/Watchdog/` | 记信号、算「可疑」，纯逻辑，好测 |
| `WatchdogJudge` | `Flyknit.Core/Watchdog/` | 拼给模型的摘要（含脱敏）、解析回答、频率上限 |
| `WatchdogPolicy` | `Flyknit.Core/Watchdog/` | 状态：正常 → 已提醒 → 已停 / 员工说不用管；决定下一步做什么 |
| 给 AI 的提醒 | `AgentLoop` 新增 `Advisory` 钩子（`Func<string?>`） | 下一个工具结果后面附上，和 `LoopGuard` 提醒同一个位置；不新增消息、不打断工具调用 |
| 每分钟检查、通知、停止 | `Flyknit.Client/Services/AgentHost.Watchdog.cs`（新 partial） | 停止调现有的 `Stop(conversationId)`；任务账本 `EndRun` 带上看门狗的原因 |
| 心跳 | `AgentHost.Watchdog.cs` + `FlyknitServerClient.HeartbeatAsync` | 有任务在跑时才发 |
| 任务中心标记 | `TasksPage.vue`、`BackgroundTab.vue` + 桥接事件 `task.watchdog` | 三语 |
| 服务端 | `routers/client.py`（心跳）、`models.py`（两列）、`usage_store.PURPOSES` 加 `watchdog`、`security_settings.py`（三项）、admin 设备列表 | |

命令行 / IDE（`flyknit -p`、ACP）本期不接：它们有自己的步数上限和 `LoopGuard`，C2 统一。

## 7. 不做的

- 不让 Watchdog 自己「接手」或改写计划（那是 Router 的事，C2）。
- 不检查专家子任务、子代理的内部步骤：它们算在主任务的步数和时间里，主任务被停时一起停。
- 服务端不判断任务内容、不远程停任务。

## 8. 测试和验收

**单元测试（Core）**：
- 进展信号：新操作、计划推进、产出文件都算进展；纯重复不算；只读操作连续很多次后降权。
- 暂停计时：工具执行中、等确认、`ask_user`、暂停期间，过多久都不判可疑（**长时间编译 / 跑测试不误伤**）。
- 可疑要同时满足「N 分钟没进展」和「至少 8 步」；慢但每步都有进展的任务不判可疑。
- 模型判断：摘要里的密钥被脱敏；回答解析不了按有进展处理；频率上限和次数上限。
- 处理：第一次只提醒；提醒后仍卡住且开了自动停止才停；员工点「不用管」后不再提醒；模型调用失败不自动停。
- 开关关着时宿主不启动检查（`SecuritySwitchTests`）。
- `AgentLoop` 的 `Advisory` 钩子：提醒附在下一个工具结果后面，只附一次。

**服务端**：心跳写入和读出、失联判定、只收任务编号和来源（多余字段丢弃）、`watchdog` 用途进白名单、三个开关的默认值和锁定。

**界面**：web build（类型 + 三语）；模拟宿主下任务中心显示「可能卡住了」和两个按钮；admin build。

**验收（Windows 实机）**：
1. 打开看门狗和自动停止、阈值设 5 分钟，故意给一个做不到的任务（比如「找出一个不存在的文件的内容，找不到就继续找」）：几分钟内收到提醒，再过几分钟被停下，任务中心写着原因，审计里有记录，后台「按用途」里有 `watchdog`。
2. 让 AI 跑一条要 15 分钟的编译或测试命令：全程不提醒。
3. 让 AI 做一件要确认的事，确认卡片放着 20 分钟不点：不提醒、不停。
4. 跑任务时拔网线超过 10 分钟：后台设备列表显示「失联（有任务在跑）」；插回去后恢复。

## 9. 风险

- **误伤**：最大的风险。对策是暂停计时、程序 + 模型双重认定、先提醒后停、默认不自动停、员工可以「不用管」。
- **成本**：只在可疑时调，单次约 2k token，每个任务最多 6 次；走便宜模型，按用途单独统计，上线后看占比。
- **模型误判跑偏**：只靠模型判「跑偏」时，第一次只提醒、不停；第二次仍要程序也判可疑才停。

## 10. 需要你确认的

1. **自动停止默认开还是关**：推荐**关**（IT 先只开提醒，看一阵误报情况再开自动停止）。总开关 `watchdog` 按你的要求默认关。
2. **模型用哪个场景**：推荐**沿用 `title` 场景**（已经配好的便宜模型），用量按用途记成 `watchdog`；也可以新增一个 `watchdog` 场景单独配模型，但 IT 要多配一项、没配时回退 `title`。
3. **多久没进展算可疑**：推荐默认 **10 分钟**、长任务模式 ×2，IT 可在 5～60 分钟之间调。
4. **心跳内容**：推荐**只报任务个数、来源和任务编号，不报标题**；如果后台想看到「在跑什么」，就要把标题当聊天内容处理，只给有「查看聊天记录」权限的账号看。
5. **手机端「电脑已离线」**这期做不做：推荐做（改动小，手机办事最需要知道电脑还在不在）；也可以推到第 5 期和手机按任务看进度一起做。
